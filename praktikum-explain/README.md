## Задача 1. Запрос без индекса

Запрос:

```javascript
db.events.find({
  service: "payments",
  level: "error",
  duration_ms: { $gt: 500 }
}).sort({ ts: -1 })
```

Он вернул 33 записи. Сервер просмотрел все 1200 документов и не просмотрел ни одного ключа индекса. В плане снизу вверх идут `COLLSCAN`, затем `SORT`: подходящего индекса нет, поэтому MongoDB перебирает коллекцию, фильтрует документы и только потом сортирует найденные 33 записи в памяти.

## Задача 2. Индекс по ESR

Разбор запроса:

- `E` (Equality): `service`, `level`;
- `S` (Sort): `ts`;
- `R` (Range): `duration_ms`.

Команда:

```javascript
db.events.createIndex({ service: 1, level: 1, ts: -1, duration_ms: 1 })
```

После индекса результат тот же: 33 записи. Просмотрено 33 документа и 43 ключа индекса. Документы просмотрены в `FETCH`, а индексная часть выполняется в `IXSCAN`. Число ключей больше числа результатов, потому что индекс сначала находит непрерывный участок по `service`, `level` и `ts`, а условие диапазона отбрасывает часть ключей по `duration_ms`.

Число просмотренных документов уменьшилось с 1200 до 33, то есть примерно в **36,4 раза**. `SORT` исчез, потому что порядок `ts: -1` уже обеспечивается индексом после двух точных условий.

## Задача 3. Почему порядок полей важен

### Вариант A: `duration_ms, service, level, ts`

Диапазон поставлен первым. Индекс просмотрел 378 ключей, извлёк 33 документа и затем выполнил `SORT`. Такой порядок не позволяет получить готовую сортировку по `ts` после фильтрации.

### Вариант Б: `service, level, duration_ms, ts`

Равенства стоят правильно, но диапазон находится перед полем сортировки. Индекс просмотрел всего 33 ключа и извлёк 33 документа, однако `SORT` всё равно остался: после диапазона индекс не гарантирует порядок по следующему полю `ts`.

В рабочей базе оставил бы индекс из задачи 2 (`service, level, ts, duration_ms`). Он соответствует ESR и убирает сортировку в памяти. Вариант Б экономнее по числу ключей на маленьком наборе, но на большом журнале сортировка может превысить лимит памяти 100 МБ.

## Задача 4. Десять самых долгих ошибок

Запрос:

```javascript
db.events.find({ level: "error" })
  .sort({ duration_ms: -1 })
  .limit(10)
```

По ESR: `level` — равенство (`E`), `duration_ms` — сортировка (`S`). Подходящий индекс:

```javascript
db.events.createIndex({ level: 1, duration_ms: -1 })
```

До индекса сервер просматривал все 1200 документов и сортировал найденные ошибки. После индекса вернул 10 документов, просмотрел 10 ключей и 10 документов; план состоит из `IXSCAN → FETCH → LIMIT`. В коллекции 180 ошибок, но читать все 180 не нужно: индекс уже хранит ошибки `level: "error"` в порядке `duration_ms`, поэтому после первых десяти записей срабатывает `LIMIT`.

## Ответы для приёмки

`totalKeysExamined` — число просмотренных записей индекса, а `totalDocsExamined` — число реально загруженных документов. `FETCH` нужен, потому что индекс содержит ключи и ссылки на документы, а не полный документ. Индекс из задачи 2 просматривает 43 ключа и возвращает 33 документа из-за проверки диапазона `duration_ms > 500`. При вставке новой записи MongoDB добавит её во все подходящие индексы, поэтому индексы ускоряют чтение ценой дополнительной работы при записи и места на диске.
